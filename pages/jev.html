Jev：一个不写字、只做判断的模型

TypeSafe AI · 2026-09-15 发布 · 创始人 Diogo Almeida（RLHF 共同发明人）｜ 前沿发布仅一周，所有数字务必看清来源
先说清我研究的是什么。你说的「JEV」我按 Jev 来理解——TypeSafe AI 在 2026 年 9 月 15 日发布的「System One」决策模型，发布一周内就在机器人圈被大量试用。如果你其实想问的是 LeCun 的 JEPA／V-JEPA 2（联合嵌入预测架构），那是完全不同的东西，说一声我再补一页。

0 · 一分钟版本

一句话：Jev 是一个「聪明的 if 语句」——你给它一段数据（state）和几个带类型的问题，它返回带概率的答案。它不写一个字的自然语言，不解释理由，不生成代码。它只做判断。

为什么它值得关注：它的创始人 Diogo Almeida 是 RLHF 的共同发明人——也就是亲手做出 ChatGPT 那套让 AI「会聊天」的方法的人。他花了四年得出的结论是：会聊天解决了人机交互，但没有解决自动化。Jev 是他对这个缺口的答案。

三个可验证的特征：

  • 延迟 70–500 毫秒（前沿大模型同任务要 3–329 秒）
  • 输入 $0.042 / 百万 token（大模型是 $0.20–$10），输出不计费
  • 结构化输出错误率 0%——但这一点要仔细读，后面会讲清楚它到底保证了什么

1 · 它要解决什么问题

先讲动机。不讲动机，你会觉得 Jev 只是「一个精简版模型」，理解不到它的野心。

1.1 一个被忽略的事实

Diogo Almeida 在发布文里问了一个问题：

「模型在聊天上超人类已经好几年了，那自动化在哪里？」

这是个很好的问题。大模型能写论文、能通过考试、能写代码，但你的生活里有多少环节真的被自动了？很少。原因是：

  • 聊天模型的目标是「让人满意」——RLHF 优化的是人类评分员更喜欢哪个回答。它没被优化成「能被软件可靠调用」。
  • 它输出的是字符串——字符串极其灵活，可以是答案、代码、也能是幻觉和拒答。软件要拿它做判断，必须先解析、再校验，而且永远有「模型跑偏了」的风险。
  • 它慢——3 到 329 秒。跟人对话够用，嵌进代码的实时循环就是死结。
  • 它过度自信——你问它有多大把握，它说 95%，但真实准确率可能是 70%。如果模型不知道自己什么时候会错，那它错的那部分就必须永远有人盯着。

1.2 于是有了「System One」这个名字

取自卡尼曼《思考，快与慢》：System 1 是快速、直觉、不费力的判断；System 2 是缓慢、需要推理的思考。

System 2 型（现有大模型 / 推理模型）System 1 型（Jev）
干什么写文章、写代码、解数学题、推理分类、路由、打分、判断真假
速度秒级毫秒级
什么时候用难问题、低频、要人看结果简单问题、高频、要自动化
为什么叫「一」而不是「二」是褒义：System 1 在心理学里常被描述成「容易出错」。TypeSafe 的判断是——对于「在有限选项里挑一个」这类任务，快速直觉型反而可以做得比推理型更可靠，因为它根本不给模型自由发挥的空间。这是整个产品的立论基础。

1.3 名字「Jev」的来历

取自经济学家 William Stanley Jevons，对应「杰文斯悖论」：蒸汽机效率提高，反而让煤炭消耗增加。

它的隐喻：智能的成本每下降一个数量级，就会解锁多一个数量级的用途。降价不是省钱的工具，是创造新需求的工具。——这也解释了为什么他们敢把输出定价为「免费」。

2 · 最核心的区别：它不写字

这一节如果你只记一件事，记这个。Jev 的所有优势，都是「放弃生成文字」换来的。

现有大模型Jev（System One）
训练优化目标人类偏好（RLHF）／可验证奖励（RLVR）校准的决策（RLCD）——答案要对，而且「说我有多大把握」也得真的准
输入形态非结构化文本，重点是对话消息非结构化文本，重点是结构化程序状态
输出形态字符串——可能是答案、代码、也可能是幻觉或拒答；软件要用必须先解析校验带类型的结构化数值——可能的输出和结构事先定义好，模型不可能产生类型错误
采样方式串行：一个 token 一个 token 地生成，每个都依赖前一个并行：一次查询里把所有答案同时算出来
成本输入 $0.20–$10 / 百万 token；输出比输入贵约 5 倍输入 $0.042 / 百万；输出免费
速度端到端 3–329 秒70–500 毫秒
置信度就算你追问，它给的置信度也常常过度自信、前后不一致每个输出都附校准过的置信度——把握说 95%，准确率就真的接近 95%
「并行采样」为什么这么重要？大模型一次只能吐一个 token，所以「回答问题 A、B、C」要串行做三次，越往后越贵越慢。
Jev 是把所有问题同时对着同一份 state 求值。TypeSafe 实测：一次调用问 13 个问题，比分成 13 次调用便宜 12.2 倍、快 10 倍（用 53,777 字符的文档测试）。省下来的钱主要来自「state 只发一次」。
这个特性直接改变了你怎么设计系统——习惯了大模型的人总是「问一个、看结果、再决定问什么」，用 Jev 时应该把可能有用的独立问题一次性全问了，哪怕有些当前输入用不上。

3 · 三种问题原语

Jev 的所有能力，都由三种问题类型拼出来。理解这三种，你就理解了这个模型。

原语问的是返回什么生活化理解
Noul 这句话是真的吗？ noul（0–1 的概率） 「这是不是退款请求？」→ 0.93
Choice 这些选项里是哪个？ choice + 完整概率分布 + confidence 「这工单归哪个部门？」→ billing
Score 在这个量表上的哪里？ score + 分层 + 完整概率分布 + confidence 「这个 bug 多严重？」→ 1.3 / 2
三种原语就够了？够了。因为所有「判断」在数学上都能拆成这三类：是不是（布尔）、哪个（分类）、多少（序数）。任何更复杂的判断，都是这三类的组合——这就是为什么它敢说「答案空间有界」是它的适用前提。

3.1 三个必须记住的实操细节

① Noul 的 0.5 不是「中等」，是「我分不清」
这是最常见的误读。想测量程度，请用 Score，不要用 Noul。另外：让「值大」对应「是」，别写成 true 表示否——反向表述会显著降低答案质量。
② Choice 必须给出口
模型必须选一个，所以当你的选项列表可能覆盖不全时，一定要加 other 或 none_of_the_above。否则它会把一个不属于任何类的东西硬塞进某类里，而你还以为分类是准的。Choice 最多支持 255 个选项。
③ Score 要描述「情境」，不要描述「程度」
这是文档里强调最多的一条。"Broken feature, but a workaround exists" 有用；"Moderately severe" 和裸数字没用。
为什么：每个层级是独立判断的，模型看不到层级编号、也看不到相邻层级。所以「比上一级更严重」这种表述对它是无意义的。
另外：一个 Score 只测一个维度，混两个维度会让 confidence 崩掉。Score 支持 2–10 个层级。

4 · 一次真实调用长什么样

看一个完整例子。假设你要处理一个赞助咨询表单：

{
  "model": "jev-latest",
  "state": {
    "name": "Managed Postgres",
    "description": "We make a managed PostgreSQL hosting product
                    and would like to sponsor the newsletter in October."
  },
  "questions": {
    "is_sponsor_inquiry": {
      "type": "noul",
      "instructions": "Does `description` ask to sponsor the site?"
    },
    "product_category": {
      "type": "choice",
      "instructions": "What kind of product is described by `name`?",
      "criteria": {
        "dev_tool": "Developer tools, hosting, APIs, SaaS for developers",
        "course": "Courses, books, or training",
        "unrelated": "Anything not aimed at developers"
      }
    }
  }
}

返回：

{
  "answers": {
    "is_sponsor_inquiry": { "noul": 0.99 },
    "product_category": {
      "choice": "dev_tool",
      "probabilities": { "dev_tool": 0.97, "course": 0.01, "unrelated": 0.02 },
      "confidence": 0.95
    }
  },
  "usage": { "input_tokens": 210, "output_tokens": 31 }
}

4.1 代码怎么用它

关键在于——模型给判断，代码决定动作。这才是「智能 if 语句」的意思：

const { answers } = response

if (answers.is_sponsor_inquiry.noul > 0.9
    && answers.product_category.choice === 'dev_tool') {
  sendRateCard(email)          // 高置信度：自动执行
} else {
  queueForManualReply(email)   // 其余：进人工队列
}
对比一下传统写法：如果你用正则或关键词匹配来做这个判断，你要写一堆 if (text.includes('sponsor') || text.includes('advertise') ...)——看起来能用，但用户换一种说法就崩。Jev 替换的正是这段脆弱的手写逻辑。
它不是「AI 变得更聪明」，它是「把一段容易坏的解析代码换成一次模型调用」。

4.2 一个容易忽略的规则

问题的 ID 不会发送给模型。is_sponsor_inquiry 这个键只给你的代码用。所以完整的问题必须写在 instructions 里——写 refund_requested 这种键名，模型是看不懂的。
这和用大模型时的直觉不同：大模型会「猜」你的意图，Jev 只读你写的字。

5 · 置信度才是真正的产品

TypeSafe 自己反复强调，也在第三方分析里被反复指出：Jev 真正值钱的不是速度也不是便宜，是校准（calibration）。

5.1 什么是校准

校准 = 它说有多大把握，就真的有多准。
说 95% 把握的事情，在真实任务里就该有约 95% 的正确率。说 60% 就该约 60%。这在工业场景不是加分项，是能不能自动化的生死线。

5.2 为什么这决定了「能不能自动」

设想一个模型能把某任务做对 95%。听起来很好，但：

  • 如果它不知道自己哪 5% 会错 → 你必须对 100% 的结果做人审 → 自动化收益归零
  • 如果它知道自己哪 5% 不确定 → 95% 自动执行、5% 转人工 → 真的省下了 95% 的人力

所以这套工作流才成立：

置信度 > 0.9
自动执行· 0.5 – 0.9
标记待审 / 让用户确认· < 0.5
转人工 / 请求澄清
阈值是你要自己定的，而且取决于「答错的代价」。TypeSafe 文档给的示例是：0.5 作为「必须复核」的下限，0.9 用于不可逆的破坏性操作。这两个是示例不是默认值——删数据库和换个标签，显然不该用同一个阈值。

5.3 置信度是怎么算出来的

它来自概率分布的形状。举个例子：某个 Choice 问题上，billing 赢了，概率 0.84，但 technical 还占 0.159——分布比较散，所以 confidence 只有 0.596。

换句话说：赢得多不算什么，「赢得干净」才代表模型真的确定。这个设计很聪明——它把「模型的不确定性」直接暴露成你可以拿来写 if 的数字。

关于「永不幻觉」，有一处必须讲清楚，否则你会被误导。
「0% 类型错误」不是实测出来的数字，是数学保证。因为所有可能的输出结构事先就定义好了——模型在数学上不可能吐出一个不符合 schema 的值。TypeSafe 自己也说：这个数字「不是经验性的」。

所以正确的理解是：Jev 保证「输出的格式和取值范围一定合法」，但不保证「它选的那一项是对的」。它可能在你给的 4 个部门里准确地选了一个错误的部门。
「不会幻觉」≠「不会错」。这是两件完全不同的事，营销话术容易把它们混起来。

7 · 它在机器人里怎么用

这是你最关心的部分。先给一个可能不太好听但必须说的判断：

Jev 不是策略模型，它不能替代 VLA，也不能做运动控制。
它没有图像、音频、视频输入（官方明确说明 Doom demo 用的是结构化状态、不是画面）。它的延迟是 70–500 毫秒，也就是 2–14 Hz——而控制回路通常需要 100–1000 Hz（1–10 毫秒）。
把它塞进电机控制回路是彻底用错了地方。

它真正的位置在「上一层」——那些「需要判断、但不需要高频」的地方：

传感器/事件/日志→ Jev 判断
要不要升级？归谁？多急？→ 代码分支→ 人 / 慢速 LLM / 执行器

7.1 已经验证过的几个位置

位置Jev 判断什么为什么合适
车队事件分诊 是否升级人工 / 归属团队 / 紧急度 有第三方实测（上面 6.3 节）。高频、答案空间有界、答错代价可控
Agent 工具调用护栏 这个 shell 命令是只读 / 可逆 / 不可逆？ 不安全操作必须被拦住。作者在自己的计划里就列了这条。有个细节值得注意：影子测试里 rm -rf 被判为「不可逆」的概率只有 0.56、置信度 0.33——这类高风险判断千万别只看结论，必须结合置信度设阈值
意图路由 这个请求该走数据库查询、还是带某类上下文的 LLM、还是人工？ 早期落地最多的场景。让便宜的路径先分流，昂贵的模型只处理真正需要的
验证 VLA / LLM 的输出 这段摘要的说法有原文支持吗？这个动作符合任务意图吗？ 用 Noul 做「有据可查」检查。把 Jev 当第二双眼睛，而不是当手
UI 元素选择 该点哪个按钮？ 浏览器/手机自动化里，让规划模型定目标、Jev 从候选元素里选。「从牌堆里挑一张牌」，这正是它擅长的形状

7.2 那个机械臂 demo 的真相

有一条流传的 demo 是「Jev 操作机械臂抓红色方块放进正确的盒子」。关键细节在手边那个 harness（外层框架）里：是 harness 向 Jev 提供了实时几何信息、接触数据、以及控制效果的预测，Jev 只是在「这些动作里挑一个」。

这个分工值得你抄。机器人系统正确的分层是：
感知与几何 → 由确定性代码做（准、快、可验证）
候选动作生成 → 由规划/RL/几何求解器做
在高层语义判断上选一个 → 这才是 Jev 的位置
反过来，如果你让 Jev 去算「末端距目标 12.3 厘米」这种数，它会错——它是决策层，不是计算层。

7.3 与你的学习路线的对照

你在学的Jev 的位置
MuJoCo / MJX 仿真训练 PPO无关。那是策略学习，Jev 不做策略
VLA（视觉-语言-动作模型）互补而非竞争。VLA 是「手和眼」，Jev 是「判断这条指令该不该执行、该交给谁」
LeRobot 采数据 / ACT 策略无关
机器人系统的工程化与运维这正是它的战场：事件分诊、异常分类、护栏、路由
对你的投资视角，它有意思的地方在于：它代表一类不跟大模型卷参数、而是卷「可靠性和单位成本」的产品策略。「智能的成本每降一个数量级，就解锁一个数量级的用途」这个杰文斯式判断，是它整个商业论证的支点。值得观察的是：它能不能在「大模型厂商顺便把这个能力做进自家 API」之前建立起护城河。

8 · 边界：别让它做的事

TypeSafe 为每个模型版本发布一份「jaggedness（锯齿面）」页面，主动列出它做不好的地方。这种坦诚在 AI 公司里很少见，也说明这些坑是真踩过的。

别让它做为什么正确做法
算数 它不是计算器，不能可靠计数——数不清字符、出现次数、列表项数 算术在代码里做，把结果或分档传给它
数数 同上。「有几个水果名？」它会答错 每个项问一个 Noul，然后在代码里求和（文档给了完整代码示例）
比较日期 它把日期当文本读，先后、间隔、是否落在窗口内都不可靠 用 Choice 分别抽月/日/年（带「未说明」选项），在代码里构建真实日期再比较
判断颜色接近 命名颜色（"红色"）可以，#FF4B0A 这种不行 颜色距离在代码里算
多跳推理 双重否定、「属性的属性」、任何需要绕一步的，准确率都下降 拆成多个直指 state 的简单问题
写东西 官方直言：可以靠字符级 Choice 硬凑出文本，又慢又差 要生成就交给 LLM。Jev 判断，LLM 写作
解释理由 只给概率数字，不给原因。这对调试和受监管行业的审计是实质限制 把它当无解释组件用，靠日志和阈值复核
一句话总结它的适用形状：
「从牌堆里挑一张牌」——可以。「让它报出牌名」——不行。
当你本能地想说「提取 X」的时候，把它改写成「这些是 X 的候选，哪个是它？」

8.1 还有一条最容易被忽略、但影响最大

给它的 state 越大、越杂，准确率越低。官方原话："A large state full of irrelevant detail costs accuracy too. Filter first."
它和别的模型一样会受上下文腐化（context rot）影响。所以：先在代码里过滤，只发问题真正需要的那部分。
举个具体例子：给单个工单打分时，不要发这个客户的完整历史；给一个段落分类时，不要发整份文档。
如果没法用确定性代码过滤，就每一块问一个 Noul：「这段和问题相关吗？」然后丢掉不相关的。

9 · 什么规模该自建

这是 RoboKrunch 做的第二个实测，我觉得是整份研究里最实用的一块——它给出了「什么时候不该用 Jev」的量化答案。

对比对象：自己部署 ModernBERT-base（1.49 亿参数）在 2 核 AMD EPYC 上，纯 CPU，单条推理。

指标ModernBERT（自建）Jev（API）
p50 延迟169.3 ms527 ms
吞吐5.06 条/秒约 1.8 次决策/秒
单次判断数1 个标签3 个判断
需要训练数据18 个样本 + 调参0
运维负担服务器你自己维护0
这组数据揭示了一个反直觉的事实：
Jev 的优势不是「推理快」——一个本地小模型比它快约 3 倍。
它的优势是「起步成本为零」：不用训练、不用标数据、不用养服务器。
一旦你跨过某个规模、标签又稳定，就该自建。

交叉点：假设 4 核 VM 每月 $24，自建在约 97.7 万次决策/月时打平——大约相当于 678 台机器人（每台每天 48 次决策）。低于这个规模，用 Jev 更便宜，而且省掉了训练、标注和运维。

但成本账有一句最重要的提醒，来自深度分析文章：
「有用的指标是每解决一个任务的成本，不是每个 token 的成本。如果便宜路径增加了重试或人工审查，节省会缩水。」
算账要算整条管道：预处理、重试、失败请求、人工复核，以及 Jev 前后那些还在跑的生成步骤。
一个真实例子：分类 1,018 篇论文摘要花 $0.08，但如果还要 LLM 去写摘要，那部分要 $3.99。分类便宜 50 倍，但摘要才是花钱的地方。

10 · 我的判断

它是什么

它不是一个更小的大模型，也不该被当成「便宜的替代品」。它是一类新的组件：把「需要理解语义的条件分支」从手写代码里拿出来，交给一个快、便宜、结构受约束的模型。

它最有价值的三个点

  1. 它把「不确定性」变成了一个可以写进 if 的数字。这是我见过的、让 AI 真正可自动化的最务实的一步。校准不是技术细节，它是「你敢不敢让它不看结果就执行」的门票。
  2. 并行采样改变了系统设计方式。一次问 13 个问题比问 13 次便宜 12 倍——这个特性要求你在设计阶段就想清楚「我可能需要的所有判断」，而不是像用大模型那样一步步问。这是个真正的范式差异。
  3. 它的输出结构是数学保证的。不是「实测错误率很低」，是「不可能不合法」。对埋在依赖链深处的组件，这是质变。

必须打的三个问号

  1. 所有漂亮数字都是厂商自报的。「193.6 倍更快 444.6 倍更省」是 TypeSafe 自己的工作流评测，他们自己也说是高端上限。目前唯一的第三方实测只跑了 300 条模拟事件，而且是分诊场景。你如果要认真评估，只能自己跑。
  2. 「不幻觉」这个说法容易被误读成「不会错」。它只保证格式合法，不保证选对。而「选错了但格式正确」恰恰是最难被发现的那类错误。
  3. 护城河问题没答案。如果 OpenAI/Anthropic 明天在自己的 API 里加一个「结构化决策」端点，并且顺带把校准做进去——Jev 的核心差异还剩多少？这个问题的答案决定它是一个公司还是一个功能。
给你的实操建议：如果你想用它，从你自己每天都做的、已经能答对的判断开始——
① 先写下来你现在的判断规则是什么；
② 用影子模式并行跑——保持现有行为不变，把 Jev 的答案全记下来；
③ 人工标对错，看置信度和准确率在哪里出现分歧；
④ 用这些数据调问题和阈值；
⑤ 先自动化低风险的那条分支，一条一条来。

还有一条反直觉但重要的：当确定性代码已经能正确判断时，不要引入模型。官方原话是——「一个不花钱的 if，胜过一次可能出错的模型调用。」

两个工程纪律：

② 把模型 ID、问题定义、criteria 和阈值当成一个整体做版本管理。任何一项改动都要重放一组已知输入来回归测试。
③ SDK 必须跑在服务端，别把 API key 放进浏览器端的 JS。

11.2 限额（写作时）

  • state + 全部问题共享约 64,000 tokens；state + 单个最长问题需塞进约 32,000 tokens
  • Choice 最多 255 个选项；Score 2–10 个层级
  • 速率：约 250,000 tokens/秒、1,200 请求/分钟（早期访问期间动态调整）
  • 早期访问目前需要排队；未开源权重、未公布参数量、不支持自部署

11.3 一句话记住它

Jev 不写作，只判断。
它把「从一堆选项里挑一个」这件事，做成了一个 100 毫秒、两分钱一千万次、而且知道自己有多确定的组件。
它不打算变得更聪明，它打算变得更便宜、更可靠、更可嵌入——而这可能才是自动化真正缺的东西。
