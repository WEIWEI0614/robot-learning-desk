2 · 从一个赋值开始

在最复杂的算法里，最基础的构件仍然是"赋值"——把右边算出来的值，放进左边这个名字里。我们从 CleanRL 里挑一行真实代码：

gamma: float = 0.99
片段是什么为什么这么写
gamma 变量名，对应强化学习公式里的符号 γ Python 里变量名只是标签。名字本身不影响计算，但叫 gamma 而不是 g，半年后你还看得懂。
: float 类型注解（type annotation），声明"这个值是小数" Python 是动态类型语言，不写也能跑。写它的作用是：① 给人看；② 给工具看——CleanRL 用 tyro 库读类型注解，自动把它变成命令行参数 --gamma。不写注解，这个参数就不会出现在命令行里。
= 0.99 赋值本身，同时是默认值 "不指定时用 0.99"。写成 0.99 而不是 0.99 之外的任何数，是因为这是 RL 里的经验值——表示"未来的奖励每往远一步就打 1% 折扣"。

2.1 为什么必须是 float 而不是 int

这是个能说明"数据类型不是小事"的好例子：

# 如果 gamma 是整数类型，只能取 0 或 1
gamma_int = 0          # 完全不要未来：只看眼前这一步的奖励
gamma_int = 1          # 未来和现在一样重要：永不衰减，训练常不收敛

# 而 float 能表达"打折"这个中间状态
gamma = 0.99         # 每远一步，权重乘 0.99
这就是"数学符号 → 代码"的第一道坎：数学里的 γ 是实数，代码里你必须挑一个能装下它的类型。挑错了，你表达不出"折扣"这个概念——这不是精度问题，是表达能力问题。

2.2 赋值到底发生了什么（跑一遍看结果）

把赋值放进循环，你就能看见"折扣"是怎么累积的：

gamma = 0.99
reward = 1.0
for step in range(4):
    print(step, round(reward, 6))
    reward = reward * gamma      # 赋值：右边算完，再放回左边
轮次打印时的 reward这一步之后 reward 变成含义
step=01.00.99当前奖励权重 1.00
step=10.990.9801一步之后只值 99%
step=20.98010.970299两步之后值 98%
step=30.9702990.960596三步之后值 96%
reward = reward * gamma 这一行值得盯三秒。它先算右边的 reward * gamma，得到新值，再赋给左边的 reward。同一个名字在等号两边，含义不同：右边是"旧值"，左边是"新值"。几乎所有"累积""迭代""更新"的代码，都是这个形状——包括神经网络的参数更新。

3 · 公式 → 代码：用 PPO 真实源码对照

这一节是整页的核心。强化学习论文里的公式看起来吓人，但落到代码上往往只有几行。看四个例子，从易到难。

3.1 例一：动作采样（从概率分布到一行）

a ~ πθ(·|s)　　a 从策略网络输出的概率分布里采样
def get_action_and_value(self, x, action=None):
    logits = self.actor(x)              # ①
    probs = Categorical(logits=logits)  # ②
    if action is None:
        action = probs.sample()         # ③
    return action, probs.log_prob(action), probs.entropy(), self.critic(x)
行代码对应公式的哪一部分为什么用这个函数
①logits = self.actor(x) 策略网络 πθ 对状态 s 的输出 self.actor 是一个神经网络，x 是观测。注意输出叫 logits 不叫 probs——网络直接吐出来的是"未归一化的分数"，不是概率。
②probs = Categorical(logits=logits) 把分数变成概率分布 Categorical 是 PyTorch 的类别分布对象。传 logits= 而不是先 softmax 再传概率，是因为 softmax 已经内置在里面了，而且数值更稳（后面 3.3 会讲这一点）。
③action = probs.sample() a ~ πθ(·|s) 里的那个"~"（采样） 公式里的波浪号是最容易被忽略的一步。它意味着"随机抽一个"，而不是"取概率最大的那个"。强化学习必须有随机性——否则永远试不到新动作，学不出东西。
④return action, probs.log_prob(action), probs.entropy(), self.critic(x) 返回四个量 一次返回四个值是为了省一次网络前向计算。四个值分别是：采到的动作、它的对数概率（算 ratio 要用）、分布的熵（算探索奖励要用）、状态价值 V(s)。
为什么返回的是 log_prob 而不是 prob？因为下一步算 ratio 要做除法，而概率可能是 1e-8 这种极小数——一连乘就变成 0，梯度就没了。取了对数之后，除法变成减法，极小值也变成普通负数。这是科学计算里最常用的"数值稳定性"手法之一。

3.2 例二：GAE 优势估计（从递推公式到倒序循环）

δt = rt + γ·V(st+1)·(1−dt) − V(st)
Ât = δt + γ·λ·(1−dt)·Ât+1 
                delta = rewards[t] + args.gamma * nextvalues * nextnonterminal - values[t]
                advantages[t] = lastgaelam = delta + args.gamma * args.gae_lambda * nextnonterminal * lastgaelam
代码片段符号逐字对应
rewards[t]rt第 t 步拿到的即时奖励
args.gammaγ折扣因子（就是第 2 节那个 0.99）
nextvaluesV(st+1)下一步的状态价值
nextnonterminal(1−dt)必须是 1 减 done：如果这一步是终止步（done=1），未来价值就该归零
- values[t]− V(st)减去当前价值，得到"实际比预期好多少"
args.gae_lambdaλGAE 的平滑系数，控制"往前看多远"
lastgaelamÂt+1上一轮迭代算出来的优势
为什么这段代码必须"倒着循环"？看公式最后一项 Ât+1——算 t 时刻的优势，需要先有 t+1 时刻的优势。所以循环只能从最后一步往回走：for t in reversed(range(num_steps))。
这种"当前值依赖下一个值"的结构叫递推。认出它，你就知道该倒序——这是公式决定代码结构的典型例子，不是程序员的选择，是数学逼出来的。

3.3 例三：PPO 的核心——被裁剪的目标函数

LCLIP(θ) = E[ min( ρt(θ)·Ât , clip(ρt(θ), 1−ε, 1+ε)·Ât ) ]
其中　ρt(θ) = πθ(at|st) / πθ_old(at|st) 
                logratio = newlogprob - b_logprobs[mb_inds]          # ①
                ratio = logratio.exp()                              # ②

                pg_loss1 = -mb_advantages * ratio                   # ③
                pg_loss2 = -mb_advantages * torch.clamp(ratio, 1 - args.clip_coef, 1 + args.clip_coef)
                pg_loss = torch.max(pg_loss1, pg_loss2).mean()      # ④
行代码公式里的哪一步为什么这么写
①logratio = newlogprob - b_logprobs[mb_inds] log ρ（ρ 的对数） 除法变减法：ρ = 新概率/旧概率，取对数后 log ρ = log(新) − log(旧)。新概率是重新前向算出来的（因为参数更新了），旧概率是采样时存下来的。
②ratio = logratio.exp() ρ = elog ρ 先减再 exp 回来，比直接除更稳。加了这行，数值上等价，稳定性上不同。
③pg_loss1 = -mb_advantages * ratio −Â·ρ（取负号） 为什么有负号？公式里是"最大化 L"，但 PyTorch 的优化器只会"最小化 loss"。所以最大化目标 = 最小化它的负数。这个负号是公式与框架约定之间的翻译。
④pg_loss = torch.max(pg_loss1, pg_loss2).mean() min(...) 取的是哪一支 注意：公式写 min，代码写 max，这不是错。因为第 ③ 步已经整体取了负号——min(正目标) 等价于 max(负目标)。取 max 的效果是"两个候选里挑更悲观的那个"，从而不让策略一次走太远。.mean() 是把一个 minibatch 里所有样本的损失取平均，对应公式里的 E[·]。
这段代码最值得学的是什么？是 torch.clamp 这一个函数。公式里的 clip(x, 1−ε, 1+ε) 在代码里就是 torch.clamp(ratio, 1-coef, 1+coef)——它把比值硬卡在 [0.8, 1.2] 区间内（ε=0.2 时）。这就是 PPO 名字里"近端（Proximal）"的全部含义：限制策略每次更新的幅度。一个数学约束，落到代码上就是一个函数调用。

3.4 例四：总损失（从三项相加减到一行）

L = LCLIP − c1·H(π) + c2·LVF
                loss = pg_loss - args.ent_coef * entropy_loss + v_loss * args.vf_coef
代码项公式项作用
pg_lossLCLIP策略损失：让好动作更可能被选中
- args.ent_coef * entropy_loss−c1·H(π)熵奖励：减去熵损失 = 鼓励熵变大 = 鼓励探索。ent_coef=0.01 是权重，控制"牺牲多少得分去换探索"
+ v_loss * args.vf_coef+c2·LVF价值网络损失：让 V(s) 估得准。估准了才能算对优势
一行代码装下了整个 PPO 的目标函数。你以后读任何强化学习论文，都可以用这个套路：先找到"目标函数"那个公式，然后去找代码里对应的 loss = ... 那一行——中间的差距，无非是"负号、平均、clamp、系数"这四种翻译。

3.5 附：张量的形状变换在干什么

        b_obs = obs.reshape((-1,) + envs.single_observation_space.shape)
        b_advantages = advantages.reshape(-1)

采样时数据是按时间步分段的（形状 [步数, 并行环境数, ...]），而训练时要把所有样本打平混在一起（形状 [总样本数, ...]）。

  • .reshape(-1) 里的 −1 意思是"这一维你自己算"：给定总元素数和其他维的大小，剩下一维自动推算。
  • 为什么要打平？因为 PPO 要随机打乱后分批（minibatch）。如果不打平，你就只能按时间顺序喂——那等于喂给网络一串高度相关的样本，训练效果差。
  • (−1,) + shape 这种写法：元组拼接。前面加一维"样本数"，后面保留原始的形状（比如观测是 4 维向量，就打平成 [N, 4]）。

4 · server.py 逐行拆解

这是我这一轮写的主交付物。按代码分块讲。

4.1 文件头：为什么第一段是文字

"""CleanRL PPO MCP server.

Every tool is bound to the upstream CleanRL repository
(https://github.com/vwxyzjn/cleanrl). No scientific logic is reimplemented
here: tools either shell out to the repository's own CLI entry point
(`cleanrl/ppo.py`) or read its source, and report the repository's outputs.
"""

三引号包起来的叫 docstring（文档字符串）。它不参与执行，但会被 Python 保存成模块的属性，可以被工具读出、被 help() 显示。

为什么这行注释格外重要：它写的是"这里没有重写任何科学逻辑"。读过前面「论文转Agent」那一页你就知道，这句话是整个 Paper2Agent 方法论的硬规矩——把设计约束写在文件最显眼的位置，是防止后来者（包括三个月后的我自己）图省事去抄一份简化版实现。

4.2 import 区：每个 import 是干什么的

from __future__ import annotations
import ast          # 解析 Python 源码
import os           # 读环境变量
import re           # 正则表达式，抓日志
import subprocess   # 启动外部程序
import sys          # 拿当前解释器路径
import time         # 计时
from pathlib import Path   # 路径操作

from fastmcp import FastMCP
import干什么用为什么需要
__future__ annotations让类型注解延迟求值允许在函数签名里写"还没定义的类名"，且省一点启动开销。是现代的默认习惯
ast把 Python 源码解析成语法树读默认超参用的——不能直接 import 那个文件，因为那样会执行它的 if __name__ == "__main__" 块，把训练真的跑起来
os读环境变量仓库路径和 Python 路径不写死在代码里，让调用方通过环境变量告诉它
re正则匹配从训练的文本输出里捞出数字
subprocess启动外部进程并拿到输出核心——真正跑训练靠它
sys拿到当前 Python 解释器路径作为"用哪个 Python 去跑"的兜底值
time计时报告这次训练花了多少秒
pathlib.Path面向对象的路径比字符串拼接更安全、跨平台
fastmcp.FastMCPMCP 框架提供 @mcp.tool() 装饰器和协议实现

4.3 全局配置：两行，但每行都有讲究

REPO = Path(os.environ.get("CLEANRL_REPO", "")).expanduser().resolve()
PY = os.environ.get("CLEANRL_PY", sys.executable)
片段作用为什么
os.environ.get("CLEANRL_REPO", "")读环境变量，读不到给空字符串用 .get() 而不是 os.environ["..."]——后者读不到会直接抛异常。这里故意不抛，是为了稍后在 _ppo_script() 里给一句人话错误提示
.expanduser()把 ~ 展开成用户主目录环境变量里写 ~/cleanrl 是很自然的写法，但 shell 展开不一定会发生（取决于怎么传进来的）
.resolve()转成绝对路径，解析 .. 和符号链接后面要把这个路径传给子进程，子进程的工作目录可能不同，必须绝对路径
sys.executable当前解释器的路径兜底：如果没配 CLEANRL_PY，就用"正在跑这个服务器的那一个" Python
为什么这两行放在模块顶层、而不是函数里？因为它们只需要读一次。放在顶层，服务器启动时就读好，之后每次工具调用直接用；放在函数里则每次调用都读一遍。这叫"配置与逻辑分离"，也是让这个文件能通过环境变量适配任何机器的方式。

4.4 正则表达式：两行抓日志

_RETURN_RE = re.compile(r"episodic_return=\[(-?[\d.]+)\]")
_SPS_RE = re.compile(r"SPS:\s*(\d+)")
片段含义
r"..."原始字符串（raw string）。反斜杠不当转义符处理——正则里大量用 \d \s，不写 r 会踩转义坑
re.compile(...)预先编译成模式对象。好处是同一模式被反复匹配时不用每次重新解析
episodic_return=\[匹配字面量 episodic_return=[。\[ 是转义——方括号在正则里表示字符集，要匹配它本身必须加反斜杠
(-?[\d.]+)捕获组。-?=可能有负号；[\d.]+=一个或多个"数字或小数点"。括号是精髓：findall 只会把括号里的内容返回出来，外面的 episodic_return=[ 只是用来定位
SPS:\s*(\d+)\s*=零个或多个空白字符（容忍 SPS: 123 和 SPS:123 两种写法）；\d+=一个或多个数字
为什么用正则，而不用 split() 或字符串查找？因为输出格式的边角情况太多：数字可能是负数、可能有空格、可能跟其他文本混在一行。split 依赖位置，格式一变就崩；正则描述的是"长什么样"，更耐改。

4.5 守卫函数：fail fast

def _ppo_script() -> Path:
    p = REPO / "cleanrl" / "ppo.py"
    if not p.is_file():
        raise RuntimeError(
            f"CleanRL script not found at {p}. Set CLEANRL_REPO to a checkout of "
            "https://github.com/vwxyzjn/cleanrl"
        )
    return p
代码作用为什么
def _ppo_script() -> Path:定义一个私有函数（名字前下划线是"内部使用"的约定）三处地方都需要"检查脚本在不在"，抽出来避免重复
REPO / "cleanrl" / "ppo.py"用 / 运算符拼路径这是 pathlib 的语法糖，等价于"拼一级路径"。比字符串拼接干净，且自动处理分隔符
if not p.is_file():检查文件是否存在用 is_file() 而不是 exists()——后者对目录也返回 True
raise RuntimeError(...)主动抛异常这里就是 4.3 埋的伏笔：环境变量为空时 REPO 是当前目录，脚本当然找不到；与其让后面报一个莫名其妙的错，不如在这里直接把原因和修法写进错误信息
f"..."f-string，花括号里可以嵌变量把实际路径 {p} 打印出来——报错时告诉你"它去哪儿找过"，比只说"没找到"有用得多

4.6 工具一：列算法（6 行）

@mcp.tool()
def list_algorithms() -> dict:
    """List the algorithm implementations shipped in the CleanRL repository."""
    d = REPO / "cleanrl"
    algos = sorted(p.name for p in d.glob("*.py") if not p.name.startswith("_"))
    return {"repo": str(REPO), "algorithm_scripts": algos, "count": len(algos)}
行代码作用与理由
1@mcp.tool()装饰器。它的作用是把下面这个函数注册给 MCP 框架，并读取它的签名和 docstring 自动生成工具描述。不加这一行，函数就是个普通函数，客户端看不到它。
2def list_algorithms() -> dict:没有参数，返回 dict。
3"""..."""docstring 会成为这个工具的"描述"，是 AI 判断"什么时候该调用它"的唯一依据。所以工具函数必须写 docstring——这是 MCP 的设计，不是风格问题
4algos = sorted(p.name for p in d.glob("*.py") if not p.name.startswith("_"))这是一个生成器表达式：d.glob("*.py") 找出所有 .py 文件，取名字，过滤掉下划线开头的（那些是内部模块），再 sorted 排序。为什么排序？不排序的话每次返回顺序可能不同，会让"返回值比对"这种验证失效
5return {...}返回字典。为什么返回 count 这个看着冗余的字段？因为验收脚本要断言返回值，有一个稳定的整数比断言一个长列表容易。这是"为可验证性做的设计"

4.7 工具二：读超参配置（10 行，用了 AST）

这个工具的目标是：不改动、不执行任何代码，把源文件里 Args 类的默认值读出来。

@mcp.tool()
def get_ppo_config() -> dict:
    src = _ppo_script().read_text()
    defaults: dict = {}
    for node in ast.walk(ast.parse(src)):
        if isinstance(node, ast.ClassDef) and node.name == "Args":
            for stmt in node.body:
                if isinstance(stmt, ast.AnnAssign) and stmt.value is not None:
                    try:
                        defaults[stmt.target.id] = ast.literal_eval(stmt.value)
                    except Exception:
                        defaults[stmt.target.id] = ast.unparse(stmt.value)
    return {"script": str(_ppo_script()), "defaults": defaults}
行代码作用为什么
1src = _ppo_script().read_text()把源文件当纯文本读进来注意这里只是"读文本"，绝不 import。import 会执行整个文件
2defaults: dict = {}准备一个空字典装结果带类型注解，让编辑器能推断类型
3ast.parse(src)把源码文本解析成语法树语法树是"代码的结构化表示"：每个类、每个赋值、每个运算符都变成一个节点对象
3ast.walk(...)把树里所有节点遍历一遍我们不知道 Args 类在文件里哪个位置，穷举最省事
4isinstance(node, ast.ClassDef) and node.name == "Args"筛出类定义，且类名是 Argsisinstance 判断节点类型——这是遍历语法树的固定套路：先按类型筛，再按名字筛
5for stmt in node.body:遍历这个类体里的每条语句类的成员就写在这里
6isinstance(stmt, ast.AnnAssign)筛出"带类型注解的赋值"AnnAssign = annotated assignment，正是 gamma: float = 0.99 这种写法对应的节点
6and stmt.value is not None排除只有注解、没有默认值的项比如 target_kl: float = None 之外，还有纯声明 x: int，它没有值可取
8defaults[stmt.target.id] = ast.literal_eval(stmt.value)把节点里的字面量转成真正的 Python 值stmt.target.id 拿到变量名（如 "gamma"）。literal_eval 是安全的求值函数——它只认字面量（数字、字符串、元组），遇到函数调用会拒绝执行，这正是它和危险的 eval() 的区别
5try / except Exception兜底有些默认值不是字面量（比如 field(default_factory=list)），literal_eval 会失败
9defaults[...] = ast.unparse(stmt.value)失败时退化成"把它转回源码文本"ast.unparse 是语法树转字符串。这样不会因为一个字段读不出来就整个工具失败，只是那个值以文本形式呈现
这一段代码最值得记住的两点：
① ast.literal_eval 而不是 eval。两者长得像，安全性天差地别：eval("__import__('os').system('rm -rf /')") 会真的执行，literal_eval 会直接报错拒绝。凡是处理"别人的文本"的场合，永远用前者。
② 读源码比硬编码值好。如果我直接把 gamma=0.99 写进工具里，等仓库更新后这个工具就会说谎——它报的还是老值。读源码则永远和当前 checkout 一致。

4.8.1 签名：参数与默认值

参数类型注解的作用
env_id: str注解不只是注释——MCP 框架会读取它，生成工具的输入 schema。客户端（AI）据此知道"这里要传一个字符串"。类型写错，AI 就会传错类型的参数

4.8.2 docstring：写给人，也写给 AI

    ... With a fixed seed and `--torch-deterministic` the run is reproducible, so
    the reported statistics can be compared against a reference run.

这段文字里有三条约束：可复现的条件、total_timesteps 的整除要求、以及"CartPole 之外的环境需要装额外依赖"。

为什么要把约束写进 docstring 而不是代码注释？因为注释只有人看得到，docstring 会进入工具描述被 AI 读到。当 AI 打算调用这个工具时，"total_timesteps 必须是 num_envs×128 的倍数"这条信息能帮它避免传一个会崩的参数。在 MCP 里，docstring 是接口的一部分，不是文档。

4.8.3 组装命令行

    _ppo_script()
    cmd = [
        PY,
        "cleanrl/ppo.py",

片段作用为什么
_ppo_script()单独调一次，只为触发检查这是"先验证前提再干活"：脚本不在就直接抛错，不要启动一个注定失败的子进程
cmd = [...]用列表而不是字符串这是安全要点：列表形式 subprocess.run 不会走 shell 解析，参数里有空格或分号也不会被当成命令分隔符。用字符串再拼 shell 命令，就是命令注入漏洞的来源
PY列表第一项是解释器路径要用装了依赖的那个 Python 跑，而不是"碰巧能跑这个服务器的那个"
"cleanrl/ppo.py"脚本相对路径配合后面 cwd=REPO，这样写命令行最短
str(int(total_timesteps))先转整数再转字符串双重转换是有意的：int() 把 10000.0 这类浮点输入截断成整数，str() 再变成命令行能接受的文本。如果直接 str(10000.0)，命令行会收到 "10000.0"，有的参数解析器会报错
"--torch-deterministic"开关型参数，只有名字没有值让 PyTorch 用确定性算法。这是"结果可复现"的前提之一
"--no-track"关闭实验追踪CleanRL 默认会往 wandb 上传。关掉，避免要求网络和账号，也避免把数据传出去

4.8.4 执行并计时

    t0 = time.time()
    proc = subprocess.run(
        cmd, cwd=str(REPO), capture_output=True, text=True, timeout=3600
    )
    wall = time.time() - t0
    if proc.returncode != 0:
        raise RuntimeError(f"cleanrl/ppo.py failed:\n{proc.stderr[-4000:]}")
片段作用为什么用这个而不是别的
time.time()取当前时间戳（浮点秒）后面相减得到墙钟耗时
subprocess.run启动子进程、等它结束、收集结果为什么不用 os.system()？它只能拿到退出码，拿不到输出——而我们正是要靠输出来提取指标。为什么不用 Popen？那是"不等待"的异步版本，这里要等它跑完
cwd=str(REPO)设置子进程的工作目录CleanRL 会把日志写到相对路径 runs/。设了 cwd，日志就落在仓库目录里，后面找得到
capture_output=True把 stdout / stderr 收进内存等价于同时设 stdout=PIPE, stderr=PIPE，但更简洁
text=True把输出按文本解码不写的话拿到的是 bytes，正则匹配还得先手动 decode()
timeout=3600最多跑 1 小时必须有。仿真训练可能因为 bug 卡死，没有超时的话这个 MCP 服务器会被一个挂起的子进程永久占住
wall = time.time() - t0结束时间减开始时间报告实际耗时
proc.returncode != 0判断子进程是否失败约定：返回 0 表示成功，非 0 表示出错
raise RuntimeError(f"...{proc.stderr[-4000:]}")把错误往上抛，附带 stderr 尾部[-4000:] 是切片：只取最后 4000 个字符。为什么只取尾部？因为 Python 的报错信息关键部分在最后（异常类型和消息），前面的调用栈又长又没用；不截断会把整段错误塞进上下文，浪费且难读

4.8.5 提取指标

    returns = [float(x) for x in _RETURN_RE.findall(proc.stdout)]
    sps = [int(x) for x in _SPS_RE.findall(proc.stdout)]
    tail = returns[-max(1, int(last_n)):]
代码作用关键点
_RETURN_RE.findall(proc.stdout)扫全部输出，返回所有捕获组findall 在有捕获组时只返回括号里的内容，所以得到的是一个数字字符串列表
[float(x) for x in ...]列表推导：逐个转成浮点正则抓出来的是字符串，必须转换才能算数
returns[-max(1, int(last_n)):]取最后 last_n 个这一行有双重保护：int() 防止传入字符串；max(1, ...) 防止传入 0 或负数——returns[-0:] 在 Python 里等于"整个列表"，是个很容易踩的坑

片段作用为什么
glob(f"{env_id}__ppo__{seed}__*")按命名规则找这次运行的日志目录CleanRL 的目录名格式是 环境名__实验名__种子__时间戳，用模式匹配捞出来

round(sum(tail) / len(tail), 3)算均值并保留 3 位小数为什么要 round 到固定位数？浮点数的完整表示有十几位，每次可能有极微小的差异。四舍五入到 3 位，能让"逐位比对"这种严格验收变得可行——这是为可验证性做的设计

"tail_returns": tail把原始数据也返回不止给结论，还给证据。出问题时你可以自己复算，而不是只能相信我

5 · 算力基准脚本逐段拆解

这个脚本的目的是"测出每秒能推多少步"。核心难点在于：JAX 是异步的——它把计算排队后立刻返回，不等算完。所以计时必须显式地"等"。

env = registry.load("CartpoleBalance")
step = jax.jit(jax.vmap(env.step))
reset = jax.jit(jax.vmap(env.reset))
片段作用为什么必须这样
registry.load("CartpoleBalance")按名字取出环境对象54 个环境都注册在表里，按名字取最方便
env.step环境自带的"推进一步"方法注意：不是我们写的。我们只是在包装它
jax.vmap(...)向量化映射：把"单个环境前进一步"变成"N 个环境同时前进一步"这是 MJX 吞吐量的来源。写一次单环境逻辑，vmap 自动批量执行
jax.jit(...)即时编译：把 Python 函数编译成高效机器码不编译的话，每一步都要走 Python 解释器，慢几个数量级。代价是首次调用有编译时间
    state = jax.block_until_ready(reset(rng[1:]))
    act = jnp.zeros((N, env.action_size))
    jax.block_until_ready(step(state, act))          # 编译 + 预热
    t0 = time.time()
    for _ in range(REPS):
        state = step(state, act)
    jax.block_until_ready(state)                     # 关键：等真正算完
    dt = time.time() - t0
片段作用为什么
jax.block_until_ready(...)阻塞，直到计算真的完成这是本脚本最关键的一行。没有它，计时测到的是"排队花了多久"，而不是"算完花了多久"——结果会虚假地高几个数量级
jnp.zeros((N, env.action_size))造一批零动作动作值本身不影响我们要测的"仿真吞吐"
jax.block_until_ready(step(state, act))先空跑一次把编译时间排除在计时之外。不预热的话，第一次调用会把 JIT 编译的几秒钟算进去，严重低估吞吐
dt = time.time() - t0得到净耗时再用 REPS * N / dt 算出每秒步数
持续负载测试里还有两个小技巧：
vm_stat 的输出用正则抓 Swapouts: 后面的数字，比较测试前后的差值——绝对数没意义（系统本来就有历史累计），增量才说明"这段负载有没有逼着系统用磁盘当内存"。
pmset -g therm 读系统热状态。它返回 "No thermal warning level has been recorded" 本身就是结论——说明负载还没让系统接近温度墙。

6 · 站点构建脚本我改了什么

build_site.py 是已有的脚本，我改了三处。关键看为什么这么改。

6.1 原来的问题：硬编码的清单

脚本里有两个地方需要"知道所有面板叫什么"：一个是面板顺序数组，一个是用正则从网址里认出面板名。原来的写法是：

# 改之前（问题所在）
var m = hash.match(/^p-(roadmap|daily|terms|links)-/);

这个正则里手写了面板名清单。结果是：某次加了 cs329a 面板，但忘了往这个正则里补——那个面板的锚点深链就一直失效，而且不报错。

6.2 改法：让清单只有一个来源

# Python 侧：把 ORDER 注入到 JS 里
SHELL_JS = (SHELL_JS
            .replace("__ORDER__", json.dumps(ORDER))
            .replace("__NAMES__", json.dumps({k: META[k][0] for k in ORDER}, ensure_ascii=False))
            .replace("__PKEYS__", json.dumps("|".join(ORDER))))
# JS 侧：从注入的数据动态生成正则
var PKEYS = "roadmap|daily|terms|hw|sim|p2a|cs329a|links";
var ANCHOR_RE = new RegExp('^p-(' + PKEYS + ')-');
片段作用为什么
.replace("__ORDER__", ...)用占位符做模板替换把"面板清单"这一个事实源固定在 Python 侧，JS 只是消费者。以后加面板只需改一处
json.dumps(ORDER)把 Python 列表转成 JSON 文本["roadmap", "daily", ...] 恰好也是合法的 JavaScript 数组字面量，所以可以直接嵌进 JS 源码
ensure_ascii=False不把中文转成 \uXXXX 转义默认会转义，中文页签名会变成一堆 \u5de5\u7a0b，文件里就搜不到中文了，以后维护很痛苦
new RegExp('^p-(' + PKEYS + ')-')运行时构造正则JS 里正则字面量 /.../ 必须在写代码时就写全，不能插变量。要用动态内容就必须用 RegExp 构造函数
"|".join(ORDER)把列表拼成 a|b|c 的形式这正是正则里"或"的语法。注意这里没有转义——面板名是我们自己定的纯小写字母，不含正则特殊字符，所以安全。如果是用户输入，就必须转义
这个改动背后是一条通用原则：同一个事实，只能有一个来源（Single Source of Truth）。原来的 bug 不是"写错了正则"，而是"同一个清单存在两份"——只要有两份，就一定会有一天不同步。修 bug 要修结构，不是修那一行。

6.3 样式作用域：为什么每个面板的 CSS 都要加前缀

多个 HTML 合并成一个页面时，所有 CSS 会混在一起。如果两个面板都定义了 table 的样式，后面的会覆盖前面的——面板之间会互相污染。

# 原脚本里的处理：给选择器加面板前缀
for s in [x.strip() for x in sel.split(",") if x.strip()]:
    if s in ("body", "html"):
        parts.append(scope)              # body/html → 直接换成面板选择器
    else:
        parts.append(f"{scope} {s}")   # 其余 → 前面加作用域

处理之后，table{...} 变成 #p-hw table{...}——只有 id="p-code-p-hw" 的面板里的表格会应用这条规则。这就是"CSS 作用域"的手工实现。

这也解释了我在写新面板时必须遵守的两条约束：
① 不能写 :root——脚本会把 :root 整块丢掉，配色统一由全局提供；
② 表头必须写 ≥2 个 <th>——页面上那段给移动端加标签的脚本，靠"首行是不是全是 th"来判断表头，少于两个就识别不到，手机上表格会失去标签。

7 · 为什么是这些函数：选型对照表

同一件事往往有好几种写法。这张表是"我为什么挑了这个"。

要做的事我用的为什么不用别的
读源码里的默认超参 ast.parse + literal_eval 不能用 import——那会执行整个文件（包括 if __name__ == "__main__" 里的训练）。不能用正则——语法变体太多。不能用 eval——会执行任意代码
运行外部程序并拿到输出 subprocess.run(..., capture_output=True) 不用 os.system——拿不到输出。不用 Popen——它是异步的，这里需要等结果
从日志里抓数字 re.findall + 捕获组 不用 split——依赖位置，格式一变就崩。不用 JSON 解析——日志不是 JSON
路径操作 pathlib.Path 不用字符串拼接——要自己处理分隔符和跨平台；Path 还能直接 .glob() .is_file()
让计算真正等完 jax.block_until_ready 不能用 time.sleep 猜——不同规模耗时不同，等短了不准、等长了浪费时间
把"单环境逻辑"变成"批量" jax.vmap 不用手写 for 循环——那样还是逐个算，拿不到并行加速；vmap 把整批当成一次运算
模型合并时避免样式冲突 给每个选择器加面板前缀 不用 iframe——会和面板切换、锚点跳转打架；不用 Shadow DOM——老浏览器兼容性差
把配置传进程序 环境变量 不写死在代码里——换台机器就要改代码；不用命令行参数——MCP 客户端配置里传环境变量更自然

8 · 可复制的最小示例

把上面这些原理压缩成两个能直接跑的最小例子。

8.1 最小 MCP 工具（十几行）

from fastmcp import FastMCP

mcp = FastMCP("我的第一个工具")

@mcp.tool()
def 加两个数(a: float, b: float) -> dict:
    """把两个数相加并返回结果。"""      # 这句话会成为工具描述
    return {"和": a + b}

if __name__ == "__main__":
    mcp.run()

三个要点：① @mcp.tool() 是注册；② 类型注解决定参数 schema；③ docstring 决定 AI 什么时候调它。

8.2 最小"包装别人代码"的模板

import re, subprocess
from pathlib import Path

REPO = Path("/path/to/repo")
NUMS = re.compile(r"结果=(-?[\d.]+)")

def 跑一次(参数: int = 10) -> dict:
    """调用仓库自带脚本，抓取它打印的结果。"""
    cmd = ["python", "main.py", "--n", str(int(参数))]   # 列表，不走 shell
    p = subprocess.run(cmd, cwd=str(REPO),
                       capture_output=True, text=True, timeout=600)
    if p.returncode != 0:
        raise RuntimeError(p.stderr[-2000:])
    vals = [float(x) for x in NUMS.findall(p.stdout)]
    return {"n": len(vals), "值": vals}
这个模板的四个要点，正好对应前面讲的四件事：
① 命令行用列表（安全）；② 显式设 timeout（防挂死）；③ 非零退出码就抛错（fail fast）；④ 返回原始数据而不只是结论（可复核）。
换任何仓库、任何语言，这个骨架都通用——变的是命令行怎么拼、正则怎么抓。
最后一条，也是最重要的一条：写"包装类"程序时，判断你写得好不好的标准，不是代码优雅，而是"能不能被验证"。
这次我的服务器之所以能通过逐位比对，靠的不是写得多漂亮，而是三个刻意的设计：固定随机种子、把统计值四舍五入到固定位数、同时返回原始数据。
能被验证的代码，才是可信的代码。
