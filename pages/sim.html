1 · 基础概念

1.1 为什么要"仿真"

训练机器人策略，最直白的办法是让真机器人反复试错。但真机试错有三个致命问题：

  • 慢——真机一次动作要几百毫秒，仿真一步只要几毫秒
  • 贵——摔一次可能坏几千块
  • 没法并行——你只有一台机器人；仿真里可以同时跑 1024 个

所以行业标准流程是：仿真里学到策略 → 再想办法搬到真机。这个"搬"的过程就是 sim2real。

1.2 物理引擎是什么

物理引擎就是"算物理的软件"：给它一个机器人模型和一个动作，它算出下一刻各个关节在哪、有没有碰撞、受力多大。

引擎特点适合
MuJoCo接触求解精确、轻量、学术界标准强化学习、机械臂、单环境精度
Isaac Sim / PhysX照片级渲染、大规模 GPU 并行视觉感知、数字孪生（需 NVIDIA 显卡，你这台用不了）
Genesis多物理（刚体+软体+流体），支持 Apple Metal布料、软体操作
NewtonNVIDIA + DeepMind + 迪士尼共建，试图统一各引擎底层引擎层，生态仍在建设
一句话记住分工：Isaac 强在逼真，MuJoCo 强在吞吐。要拍照级数据用 Isaac，要快速迭代物理用 MuJoCo。它们不是替代关系，是分工关系。

1.3 机器人模型文件（MJCF / URDF）

引擎需要一个文件告诉它"这个机器人长什么样"：有几根连杆、每个关节在哪、质量多少、限位多少。

  • URDF——通用格式，ROS 生态用得多
  • MJCF——MuJoCo 自己的格式（XML），表达力更强（能写执行器模型、接触参数）

我们看到报错 Error opening file 'mjx_panda.xml'，就是模型文件缺失——不是代码问题。

1.4 MJX 是什么，为什么它改变了一切

MJX = MuJoCo 的 JAX 版本。关键变化在于：

普通仿真器一次只能推进一步；MJX 能在 GPU/加速器上把"1024 个机器人同时推进一步"当成一次运算。
这叫"并行环境"（vectorized environments）。对强化学习来说这是数量级的差别——因为 RL 需要的样本量极大，收集速度直接决定你能不能在一天内完成一轮实验。

上面的实测数据会看到：1 个并行环境 361 步/秒，1024 个并行环境 28.7 万步/秒——吞吐提升近 800 倍（注意：不是线性 1024 倍，因为单环境时有固定开销摊不平）。

1.5 PPO 是什么

PPO（近端策略优化）是强化学习里最常用的策略梯度算法。用大白话说：

  1. Rollout（采样）：拿当前策略在仿真里跑一批动作，记录"什么状态 → 做了什么 → 得到多少奖励"
  2. 算优势：判断"这次动作比平均水平好还是差"
  3. 更新：调整网络，让好的动作概率变大、差的变小
  4. 限制步幅：不让一次更新改变太多（这是"近端"的含义），否则训练会崩
  5. 重复 1–4

几个你一定会遇到的词：

词意思
rollout / unroll一次采样跑多少个时间步
env steps（环境步数）总共让仿真走多少步——这是衡量训练量的通用单位
timesteps同上，常混用
on-policy只能用"当前策略"产生的数据来更新——所以数据和更新交替进行，不能反复利用旧数据
eval中途停下来，用独立环境评测当前策略的真实表现

1.6 JIT 编译：为什么第一次跑特别慢

JAX 的工作方式是"先编译，再执行"。第一次调用一个函数时，它会追踪整个计算图并编译成机器码——这个过程可能几秒到几分钟。之后同样的调用就直接执行，快得多。

实用推论：你看到"第一分钟几乎没动静"是正常的，不是卡死。这也解释了为什么小规模训练（例如 2000 步）的总耗时居然要 6 分钟——大头是编译，不是计算。所以调试时别用小规模来"估时间"，会严重高估。

1.7 sim2real 差距从哪来

仿真和真机之间的差异，主要来自四个地方：

来源具体是什么
物理参数不准仿真里的摩擦系数、质量、电机力矩曲线都是估的，真机不一样
控制延迟仿真里"发指令立刻生效"；真机有通信延迟、电机响应延迟
传感器噪声真机 IMU 有噪声和漂移，仿真里通常很干净
未建模的效应线缆拉扯、结构形变、电池电压下降导致力矩变弱

对应的对策是 域随机化（Domain Randomization）：训练时故意随机化这些参数（质量、摩擦、延迟、噪声），让策略见过各种情况，从而对真实世界的差异更鲁棒。这就是训练脚本里 --domain_randomization 这个开关的作用。

2 · 我做了什么：7 步排错链

这一节是"我到底操作了什么、为什么这么操作"的完整还原。它比结论更有用——因为这套排错方法你以后装任何科学计算环境都用得上。

Step 1 · 装 MuJoCo 本体

做了什么：建隔离虚拟环境，装 mujoco，验证版本。

python3 -m venv <环境目录>
<环境>/bin/pip install mujoco
>>> 3.13.0   ✓

为什么先装它：MuJoCo 是地基，没有它后面什么都跑不了。而且它依赖最少，最容易确认"基础环境是干净的"。

Step 2 · 装 MJX，确认加速后端

做了什么：装 jax + mujoco-mjx，打印可用设备。

>>> jax 0.11.2
>>> devices [CpuDevice(id=0)]     ← 只有 CPU
>>> mjx OK
这里第一个重要结论就出来了：只有 CPU 设备。
Apple Silicon 的 GPU 走的是 Metal，而 JAX 的 Metal 后端（jax-metal）已经停止维护，所以在 macOS 上 JAX 家族（MJX、brax）基本只能用 CPU。
这意味着：你看到的吞吐数字全部是 CPU 的成绩。M4 的 10 核 GPU 在这条线上帮不上忙。

Step 3 · 想装 Playground，结果包名不对

做了什么：pip install mujoco-playground → 报"找不到包"。试下划线版 → 还是找不到。查 PyPI → 404。

为什么：这个项目不在 PyPI 上（或者发布方式变了），必须从源码装。而且它的项目名和模块名不一样——项目叫 playground，import 的时候叫 mujoco_playground。

git clone https://github.com/google-deepmind/mujoco_playground.git
pip install ./mujoco_playground          # 源码安装
python -c "from mujoco_playground import registry; print(len(registry.ALL_ENVS))"
>>> 54                                   # 54 个环境注册成功
教训：官方 README 写得清清楚楚是 pip install playground，但我实测 PyPI 也拿不到。源码安装是这里唯一可行的路径。遇到"找不到包"先别怀疑网络，先怀疑包名。

Step 4 · 训练一跑就崩（第一次）

报错：AttributeError: jax.device_put_replicated is deprecated

诊断：这是版本不兼容。brax（Playground 依赖的训练库）用的 API，在新的 JAX 里被删掉了。

先尝试的办法（错了）：直接改 brax 的源码，把废弃的 API 换成新的。

结果：改完第一层，立刻在更深的地方炸出第二个错（addressable_shards 相关的形状错误）。

这里是最值得记住的一步。我当时的做法是"打补丁"，但这在科学计算栈里几乎注定失败——因为依赖是层层咬合的，你看到的第一个错误只是最外面那一层。正确的做法是回到"哪个版本组合是被验证过的"。

Step 5 · 找到权威版本组合（关键转折）

做了什么：不再猜，直接去翻 Playground 仓库里的 uv.lock 锁文件。

这是我整个流程里最关键的一个动作。 uv.lock 是项目自己维护的"经过测试的完整依赖版本清单"。它比 README、比 PyPI 的"最新版"、比任何人的博客都权威——因为这是作者自己跑通过的那一套。

查出来的结果：

jax        = 0.6.2     ← 我用的是 0.11.2，差了 5 个大版本
jaxlib     = 0.6.2
flax       = 0.11.2
ml-dtypes  = 0.5.4
numpy      = 2.4.0

按这个组合重建环境后，训练一次通过。

Step 6 · 训练跑完了，卡在录视频

报错：RuntimeError: Program 'ffmpeg' is not found

诊断：训练本体已经完成（checkpoint 已经落盘），只是最后一步"渲染一段评估视频"需要 ffmpeg 这个外部程序。

怎么处理：这不是核心问题——训练结果已经产出。要视频就 brew install ffmpeg，不要视频就忽略。

为什么值得记一笔：报错的位置在流程最末端，容易让人误以为"训练失败了"。实际要看的是checkpoint 有没有落盘——落盘了就说明前面全成功了。

Step 7 · 想单独加载环境做推理，又缺一个包

报错：ModuleNotFoundError: No module named 'mujoco_warp'

诊断：Playground 的依赖声明里漏了 mujoco-warp（只声明了它的底层依赖 warp-lang）。

解决：pip install mujoco-warp。装完之后推理测试通过。

3 · 为什么"锁版本"是这门手艺的命门

一个真实案例，代价是 86 个百分点。
2025 年 12 月 5 日，MuJoCo 发布 3.4.0，更新日志里只有一条：修正了盒-盒距离计算。这个改动导致某个基准测试（LIBERO）上一个完全没变的模型，成功率从 98% 直接掉到 12%。另一个 checkpoint 从 80% 掉到 28%。
代码一行没改，模型一个参数没动，成绩崩了。

这就是为什么：

  • 不要相信"最新版最好"。科学计算栈的兼容性极脆弱，最新版往往是最不稳的。
  • 安装时锁到具体版本号（== 而不是 >=）。
  • 在代码开头断言实际版本，别让依赖解析器替你决定跑的是哪个版本。
  • 先找 lock 文件。有 uv.lock / poetry.lock / requirements.txt 的项目，直接照着装，不要自己配。
"可复现"不是学术洁癖，是工程底线。如果你的结果依赖"当时恰好装的是哪个版本"，那这个结果无法被验证，也无法被信任。这一条在投资尽调里也是硬伤——一个连环境都锁不住的团队，它的实验数据你敢信吗？

5.1 该上云的门槛

出现下面任何一条，就不要在本机硬扛了：

  • 单次训练预计超过 4 小时
  • 模型参数超过 10 亿
  • 需要显存超过 10 GB
  • 需要反复试参数（本机一天只能跑一两次，云上可以并行开几个）

对应选择：RunPod / Hugging Face Jobs 这类按小时租 GPU 的服务。MuJoCo Playground 官方文档也是这么建议的（训练跑在云上，导出的策略再拷回本机部署）。

5.2 磁盘与内存的余量

资源当前要注意的
磁盘可用92 GB一个大模型 fp16 权重就 14 GB；数据集和 checkpoint 也要空间。别把磁盘用到 90% 以上——SSD 满了会变慢且影响寿命。
内存16 GB（可用约 9–11 GB）系统本身要占 4–6 GB。训练模型时不要同时开一堆浏览器标签页。
交换空间2 GB（已用 0.7 GB）交换是 macOS 的"应急内存"，会把内存内容写到磁盘。大量交换 = SSD 高写入 + 明显变慢。

6 · 硬件安全边界：怎么跑不会伤电脑

6.1 先破除一个恐惧：不会"烧坏"

Apple Silicon 有硬件级过热保护。芯片温度到了阈值会自动降频（性能下降但继续工作），再高会强制休眠。你无论如何写代码，都不可能把 CPU/GPU 烧掉。这不是厂商的宣传，是芯片设计的基本机制。
我在 7 分钟满载测试里读到的系统热状态是"无热警告记录"——也就是说这个负载根本没让它接近温度墙。

6.2 真正会受损的两件事

风险机制怎么防
SSD 写入磨损 内存打满后系统会把数据反复写到磁盘（swap）。SSD 有写入寿命上限（TBW）。频繁交换 = 持续大额写入。 盯住 swap 用量：sysctl vm.swapusage。看到 used 持续上涨就是内存不够了，立刻停训练、减小 batch 或并行数。
电池加速老化 锂电池在高温 + 高电量状态下容量衰减更快。长时间满载训练正好同时满足这两个条件。 插电时训练，放在硬表面上（桌子，不是床/沙发/腿上——那会堵住底部散热）。

6.3 具体操作建议

  • 单次连续负载控制在 30 分钟以内，中间断开让机器散热。7 分钟不降频不代表 1 小时不降频——这是无风扇机型最需要守的一条。
  • 用 1024 并行而不是 64 并行。同一个任务，1024 并行比 64 并行快约 17 倍（实测）——更快跑完 = 发热时间更短，对硬件反而更友好。
  • 每次长时间训练前，先看 swap：sysctl vm.swapusage。如果 used 在涨，说明配置超出了这台机器的内存能力。我实测的负载是 0 次交换，说明倒立摆级任务完全安全。
  • 别在软表面上跑训练。MacBook Air 靠机身散热，堵住底部等于堵住散热。
  • 用电池跑重负载是双重损失：既损耗电池，又可能因为电池供电降频。
  • 大任务上云。把本机当成"调试和验证机"，把重训练交给租来的 GPU。这才是这台 Air 的正确用法。
一句话总结硬件问题：这台 MacBook Air 不会因为跑训练而损坏，但它的散热设计本来就不是为持续满载准备的。正确的用法是"短时、爆发式、小规模验证"；持续几小时的重训练请上云。
真正需要你主动防的只有一件事：别让内存打满导致大量 swap——因为那是唯一会留下永久痕迹（SSD 磨损）的操作。

7.3 训练（小规模验证用）

cd /tmp/mujoco_playground
$V/python learning/train_jax_ppo.py \
  --env_name CartpoleBalance \
  --num_envs 1024 \
  --num_timesteps 2000000 \
  --num_evals 4 --num_eval_envs 32 \

三条经验：
① --num_envs 尽量给大（1024 比 64 快 17 倍）；
② 不要用 --log_training_metrics——我在小规模 eval 下用它触发了一个 KeyError: 'eval/episode_reward'；
③ 想要评估视频就 brew install ffmpeg，不要也不影响训练结果（checkpoint 照常落盘）。

7.4 训练稳不稳的判断标准

  • 看 checkpoint 有没有落盘——落盘了说明训练本体成功，末尾的视频渲染失败可以忽略。
  • 看 eval 回报曲线是否上升——这是唯一真正的成功标准。回报不涨，环境配得再对也没用。
  • 看 swap——sysctl vm.swapusage，used 持续上涨就减小规模。
